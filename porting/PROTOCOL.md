# 广播协议与实测参数（v1.6 现场验证版）

所有结论都在真机上验证过：Android 端 App、信标 `48:87:2D:9E:6D:FB`（龙雀/DX，DA14531 芯片）。
括注的数字是实测值，不是估算。

---

## 1. 广播包结构

一颗信标一轮里会**交替发三种帧**（一个射频，一包装不下两套帧）：

| 帧 | 位置 | 用途 |
|---|---|---|
| iBeacon（厂商私有 `0x4458`） | Manufacturer Specific Data（AD 类型 `0xFF`） | 主力识别帧 |
| iBeacon（Apple `0x004C`） | 同上 | 兼容苹果生态，内容与上一条基本相同 |
| Eddystone-TLM | Service Data（AD 类型 `0x16`，UUID `0xFEAA`） | **电池电压就在这里** |

所以「电量」和「身份」不在同一包里，扫到 TLM 的那一包不含 UUID，只能靠 MAC 关联——这点和官方 TLM 规范一致。

### AD 结构遍历

```
[长度][类型][数据...]  长度 = 类型字节 + 数据字节数
```

`0x00` 表示填充结束；长度越界要停（有的设备会把包截断）。

## 2. iBeacon

```
1A FF <company:2 LE> 02 15 <uuid:16> <major:2> <minor:2> <tx:1>
```

- `1A` = 长度 26，`FF` = 厂商自定义，`02 15` = iBeacon 固定前缀。
- `company` 在空口上**小端**：苹果是 `4C 00`，这家厂商是 `58 44`（= `0x4458`）。
- `uuid` 是大端原序（直接按字节拼成 UUID 字符串）。
- `tx` 是**有符号** byte，单位 dBm，1 米处的标定 RSSI，这颗信标是 `0xC7` = **-57 dBm**。

> Android 侧早期只认 `0x004C`，改掉以后能同时看到同频段的其它 iBeacon（更利于排查）。

---

## 3. Eddystone-TLM（明文，帧类型 `0x20`）

Service Data 载荷固定 14 字节：

| 偏移 | 字段 | 说明 |
|---|---|---|
| 0 | 帧类型 | `0x20` 明文；`0x21` = EID 加密，**没密钥，解出来是噪声，直接丢弃** |
| 1 | 版本 | 固定 `0x00` |
| 2–3 | 电压 | 1 mV/bit；全 0 = 不支持（USB 供电） |
| 4–5 | 温度 | 有符号 8.8 定点；`0x8000` = 不支持 |
| 6–9 | 广播计数 | 开机以来所有类型的包数 |
| 10–13 | 运行时间 | 单位 0.1 s |

厂商会在这 14 字节后面**再追加 5 字节**（major / minor / tx），解析时在偏移 13 处截断即可。

### 真机原始帧（逐字段对拍过）

```
17 16 | AA FE | 20 00 | 03 0C | 1D 00 | E5 06 00 00 | 1C 05 00 00 | 00 05 00 06 C7
        uuid    帧/版本  电压     温度     adv 计数       运行 130.8s   ↑ 厂商追加，忽略
```

| 字段 | 字节 | 正确读法 | 结果 |
|---|---|---|---|
| 电压 | `03 0C` | **小端** | `0x0C03` = 3075 mV（大端读是 780 mV，假） |
| 温度 | `1D 00` | **大端** | `0x1D00/256` = 29.0 ℃ |
| 计数 | `E5 06 00 00` | 小端 | 1765 |
| 运行 | `1C 05 00 00` | 小端 | 1308 → 130.8 s |

### 字节序：规范和这家固件不一样

官方规范写的是**全部大端**（`tlm-plain.md`：*All multi-byte values are big-endian*），
但这批 DX 固件把电压 / 计数 / 运行时间写成了**小端**，只有温度老实按大端。

不要写死方向，按数值合理性判定：

| 情形 | 处理 | 可否落盘记忆 |
|---|---|---|
| 只有一个方向落在 **2700~3400 mV** | 用这一端 | 可以（铁证） |
| 两端都落在区间 | 优先小端 | 不可以 |
| 两端都不在区间 | 取较小的值（读反几乎只会放大 256 倍） | 不可以 |

选这个区间之后，「两端同时合理」在数学上不可能出现：需要高字节 ∈ `0x0A~0x0D` 且低字节 ∈ `0x8C~0xFF ∪ 0x00~0x48`，互斥。所以正常帧一定是单端合理。

**但结论仍建议按 MAC 记住**（Android 端存在 `shared_prefs/tlm_endian.xml`，值 `LE`/`BE`）：
电池掉到 2700 以下、或偶发被干扰的包会让单帧变成「两端都不合理」，此时靠缓存才不会来回翻方向。

温度单独处理：默认大端，读出不在 -40~125 ℃ 才反过来试小端；`0x8000` 直接当不支持。

## 4. 电量档位与显示

| 电压 | 档位 | 界面语义 |
|---|---|---|
| ≥ 3000 mV | 充足 | 绿色 |
| 2900–2999 mV | 一般 | 黄色 |
| < 2900 mV | 偏低，建议换电池 | 红色 |
| 无 TLM / 电压 0 | 无电量信息 | 灰 |

- 显示用**三位小数伏特**（`3.070v`），不做百分比——百分比是算出来的，会骗人。
- 采样取**最近 3 条平均**：单条会被发射瞬间的电流脉冲带偏几十毫伏。
- 落库做节流：**距上次写入 ≥ 1 小时**才写一次，其余只更内存。

> 别去读标准 GATT 电池服务 `0x2A19`：这些信标恒返回 64（=100%），是假数据。

## 5. 品牌判别（决定推荐 TLM 周期）

```
龙雀：UUID 去掉连字符、转大写后，前 20 个 hex 位以 E2C56DB5DFFB48D2B060 开头
```

| 品牌 | 推荐 TLM 周期 | 说明 |
|---|---|---|
| 龙雀 | 1500 ms | 固件最快/最大只能设到 1500 |
| 其它 | 6000 ms | 官方示例是 10 s，这里取更快的折中 |

规范没有强制值：TLM 章节只说「按用途决定比例」，Google 工程师给的示例是 10 s 一帧，并强调只是示例。

## 6. 实测数据（iBeacon 1000 ms + TLM 1000 ms，90 帧 / 94 s）

| 帧类型 | 帧数 | 平均间隔 | 中位间隔 |
|---|---|---|---|
| TLM | 41 | 2349 ms | 2000 ms |
| iBeacon DX（0x4458） | 27 | 3385 ms | 3515 ms |
| iBeacon Apple（0x004C） | 22 | 4215 ms | 3998 ms |

合计 **0.96 帧/秒**（配置是 2 帧/秒）——三种帧抢一个射频，谁都不是标称值。

**这意味着**：判定「到没到」时，单帧间隔按 3.5 s 估，不要按 1 s 算。

### 扫描降频（这次踩得最惨的坑）

| 状态 | 收到的包 |
|---|---|
| 连续扫描十几秒后（Android） | **0.48 包/秒** |
| 每 9 秒停/启一次扫描 | 约 60 包/9 秒（环境设备多时 300–600） |

macOS 的 CoreBluetooth 没这么激进，但长时间跑同样建议定期重建 scanner。

## 7. 在家检测参数建议

| 参数 | 建议值 | 理由 |
|---|---|---|
| RSSI 采样窗口 | 最近 5 帧取**中位数** | 均值会被个别极端值拖走 |
| 进入门限 | ≥ -75 dBm | 门内 1–3 米量级 |
| 离开门限 | ≤ -88 dBm | 与进入门限隔 13 dBm，形成滞回 |
| 进入确认时间 | 持续 **10 s** | 排除路过（快递、邻居） |
| 离开确认时间 | 连续 **60 s** 无包 | 容忍丢包和中间去阳台 |
| 距离估算 | `d = 10 ** ((ref - rssi) / 20)`，ref = -57 | 只能定性，不要用来算米 |

滞回 + 双条件是这个场景的关键：只看 RSSI 单帧一定会误报，孩子站在门口系鞋带都能触发三次。

**先测后调**：拿 `scan_probe.py` 跑 30 分钟，让娃真的进出门一次，看实际 RSSI 落在什么区间，再改门限。仓里的默认值只是起点。

## 8. 信标二维码（`KIDLINK:v1:`）

App 里「分享此信标」生成的二维码，内容是明文文本：

```
KIDLINK:v1:<Base64(JSON)>
```

JSON 全部用缩写 key（省二维码格子）：

| key | 含义 | 备注 |
|---|---|---|
| `n` | 名字 | 「书包」 |
| `r` | 备注 | 可空 |
| `u` | UUID | **32 位小写 hex，不带横线**（App 的 `getUuidRaw()`） |
| `ma` | major | 整数 |
| `mi` | minor | 整数 |
| `rs` | 1 米标定 RSSI | 缺省 `-59`，算距离用 |
| `mc` | 蓝牙 MAC | 同品牌信标三件套可能完全一样，靠它区分两台设备。**老码可能没有** |

校验规则（和 App 保持一致）：`u` 不足 32 位就整条拒收。

### 另外两种码，Mac 端不需要

| 前缀 | 是什么 | 谁用 |
|---|---|---|
| `KIDLINK:b1:` | 整套配置（娃 + 全部信标，分页轮播 `<id>:<i>/<n>`） | 换手机 / 配第二台手机 |
| `KIDLINK:cfg1:` | 推送通道、冷却、距离阈值等设置 | 同上的换机同步 |

Mac 只要一颗信标，所以只需要认 `v1`。遇到另两种前缀要**明确提示**「这是整包/设置码」，
而不是当成坏码或者硬解出一堆错字段。

### 分享路径

手机「分享此信标」→ 复制文本 / 微信提取文字 → 存成 `kidlink_beacon.txt` → AirDrop 或局域网传给 Mac
→ `scan_probe.py --qr-file ~/kidlink_beacon.txt`。

解出来的 MAC 优先用来过滤；没有 `mc` 的老码就靠三件套认（注意 TLM 帧不含 UUID，
得先在 iBeacon 帧上认出 MAC，之后同 MAC 的 TLM 才放行）。
